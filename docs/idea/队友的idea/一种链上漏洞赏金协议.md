# 项目概述
一个链上漏洞赏金协议
白帽在链下模拟攻击 用零知识证明“存在一笔不公开的交易 能改变受保护合约的关键状态”
赏金合约自动验证 把赏金打到披露者指定地址 并暂停该合约 直到项目方介入

# 痛点
白帽在生产环境发现可造成资金损失或权限接管的漏洞时 通常只有两条路
- 不攻击 链下披露： 项目方响应处理之前 漏洞仍留在生产环境 同一条攻击路径可能被黑帽利用 披露渠道还常常要求KYC或可关联身份 泄露白帽隐私
- 先实施攻击转走资金 再链上谈判：属于未经授权的状态变更和占有 事后退一部分留一部分 容易被认定为敲诈——赏金没有事先敲定 兑付和透明度都靠协商
2026年9月的[L-BTC攻击事件](https://x.com/Blockstream/status/2098281867908690394)暴露了这一痛点
攻击者从联邦钱包提走3996BTC 在链上自称白帽 协助修补后归还3400BTC 单方面留下598.5BTC
没有事先约定的赏金规则 行业目前靠的是攻击者善意 而不是机制

# 解决方案
## 验证漏洞真实性
利用[RISC0-ethereum](https://github.com/risc0/risc0-ethereum)项目 验证“存在一笔未公开交易 可使受保护合约进入异常状态”
“异常状态”在合约部署时定义
包括但不限于 某代币余额被抽至阈值以下 合约owner更改
## 发放白帽赏金
赏金事先锁在赏金合约里 规则公开
验证通过后打到披露者指定的地址
\* 提交需采用commit-reveal 以防止frontrun
## 应急响应处理
调用受保护合约预先授权的暂停函数 暂停后等待项目方人工处理
## 后处理
项目方用Input Message或BlockChat联系白帽 核对问题并协助修复
合约已经暂停 漏洞无被利用风险
